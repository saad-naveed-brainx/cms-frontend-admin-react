### Low (1)
- **src/AddPerson.tsx:327** — `ref={index === 0 ? firstBox : undefined}` always targets the first website checkbox. When the typed email already has access to the first website (e.g. `tom@kettle.test` with Café disabled) and the user submits with no website ticked, `firstBox.current?.focus()` is called on a `disabled` input. Browsers silently ignore `focus()` on disabled form controls, so the user's focus does not move to the error region. The visible `.field-error` and `aria-describedby` association still deliver the message to sighted and screen-reader users once they re-enter the fieldset, but keyboard-only users may be left wondering why the submit "did nothing". Consider targeting the first *enabled* checkbox instead (filter `team.websites` for `!hasAccess(site)` and assign the ref on the first match). *(accessibility / UX)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Resolved. A new derived `firstOpen = team?.websites.find((site) => !hasAccess(site))` (src/AddPerson.tsx:96, with a comment at :95 explaining the intent) is now the ref target: `ref={site.id === firstOpen?.id ? firstBox : undefined}` (src/AddPerson.tsx:327). When the first site is already-access, the ref skips the disabled checkbox and lands on the first enabled one, so `firstBox.current?.focus()` on validation failure moves focus into the fieldset. If every website is already-access, `firstOpen` is `undefined` and no checkbox gets the ref — but that path cannot be reached because the websites-ticked error only fires when `chosen.length === 0`, which coexists with "at least one enabled site exists" (otherwise the submit is a no-op by design).
